1. System Overview

PBAS Frontend is a browser-based Budget Automation System built for college budget, payroll, resource request, internal revenue, reporting, user management, notification, audit, and profile workflows. The frontend communicates with a backend REST API using JSON requests and bearer-token authentication.

The system is organized as protected modules. A user logs in, the session token is stored in browser local storage, and the protected area shows only those navigation modules for which the logged-in user has matching permissions.

Main Modules Included

  • Dashboard
  • User Management
  • Resource Request Management / Requests & Approvals
  • Budget Management

1A. Problem Statement

Manual budget and payroll handling in an educational institute creates delays, calculation mistakes, missing records, weak tracking, and difficulty in preparing reports for approval authorities. Requests for resources, government grants, internal revenue records, staff payroll, and annual estimates are usually handled through separate papers, spreadsheets, or informal communication. This makes it hard for the Head of Institute, Admin Officer, Accountant, and Office Assistant to know the current status of approvals, remaining budget, utilized amount, payroll commitments, and audit history.

The Budget Automation System solves this problem by providing a centralized web-based platform where users can perform their assigned financial and administrative tasks according to role-based permissions. The system improves transparency, reduces repeated manual calculation, keeps workflow status visible, and supports decision-making through dashboard analytics and reports.

1B. Project Objectives

  • To automate budget creation, categorization, year-wise tracking, and remaining-balance visibility.
  • To provide a structured request workflow where requests can be created, submitted, verified, approved, or rejected.
  • To support role-based access so each user sees and performs only authorized actions.
  • To maintain payroll staff records including BPS/rank, basic pay, allowances, deductions, increment date, and increment rate.
  • To calculate payroll estimates automatically using first 4 months salary, next 8 months salary, and increment impact.
  • To deduct saved payroll estimates and paid payroll amounts from annual payroll allocation for better financial planning.
  • To manage internal revenue in a spreadsheet-like format with automatic totals and closing balances.
  • To provide dashboard summaries, charts, status indicators, reports, CSV export, notifications, and audit log visibility.
  • To reduce paper-based work and improve traceability of financial decisions.

3. Authentication and Session Flow

  1. User opens /login, which displays the responsive splash screen.
  2. Clicking the login button opens /login/form.
  3. User submits email and password. The frontend posts to POST /api/v1/sessions.
  4. On success, backend returns user and token. Redux stores both and persists them in localStorage.authState.
  5. Protected routes validate existing token by calling GET /api/v1/session.
  6. If validation fails or any API returns 401, the frontend removes local auth state and redirects to login.
  7. Logout writes an audit-log request if possible, clears Redux/localStorage auth state, and returns the user to login.

5. Dashboard Workflow

The Dashboard loads live summary data from GET /api/v1/dashboard. It shows top-level budget, revenue, request, payroll, and notification indicators.

  • Budget totals show total, remaining, and utilized amounts.
  • Internal revenue totals show total, remaining, and utilized revenue values.
  • Pending approvals and recent activities are shown as operational signals.
  • Recent activity records are shown in a table with colored status tags.
  • The budget chart is calculated client-side by converting remaining and utilized values into percentages and SVG circle stroke offsets.

8. Budget Management Workflow

Budget Management handles budget setup, year ranges, amount tracking, and audit preview.

  • Budgets load from GET /api/v1/budgets.
  • Budget creation uses POST /api/v1/budgets.
  • Budget updates use PATCH /api/v1/budgets/:id.
  • Budget deletion uses DELETE /api/v1/budgets/:id.
  • Each budget has name, start year, end year, amount, type, head, and category.
  • Duplicate category/range overlap is checked in frontend before save.
  • Previous-year archived budgets cannot be edited or deleted.
  • Summary cards calculate total budget, remaining amount, utilized amount, year totals, and filtered totals using useMemo.

9. Payroll Management Workflow

Payroll Management covers staff master data, payroll cycles, payment tracking, payslips, annual allocation, archive lock, and estimated payroll budgets.

Staff Master

  • Staff records include full name, father name, CNIC, personnel number, post, department, employment type, staff category, BPS, gender, contact, email, bank, increment date, increment rate, active status, pay fields, deductions, and notes.
  • Staff save uses POST /api/v1/payroll_staffs or PATCH /api/v1/payroll_staffs/:id.
  • Staff deletion uses DELETE /api/v1/payroll_staffs/:id.
  • Rank-based deduction is suggested by BPS and basic pay: BPS 20 and above, BPS 17-19, BPS 11-16, BPS 5-10, and BPS 1-4 use different formulas.
  • A bulk import button imports visible payroll-sheet staff into Staff Master using the existing create-staff API.

Payroll Cycles

  • Payroll cycles load from GET /api/v1/payrolls.
  • New cycle stores month, year, notes, and annual government allocation.
  • Generate cycle calls PATCH /api/v1/payrolls/:id/generate.
  • Approve and reject cycle use PATCH /api/v1/payrolls/:id/approve and reject.
  • Payment status for each payroll item is updated through PATCH /api/v1/payroll_run_items/:id.
  • Paid amount is deducted from annual payroll allocation in local annual summary calculations.
  • Archived years lock future changes and record surrendered remaining balance.

Payroll Estimates Management

The Estimates Management tab calculates estimated payroll budget from staff master data.

CalculationFormula
First 4 months salarymonthly_basic_pay x 4
Next 8 months salarymonthly_basic_pay x 8
Increment impactincrement_rate x 6
Total estimated salaryfirst 4 months + next 8 months + increment impact

Saved estimates are stored in browser localStorage under payrollEstimatedBudgetsV1. The annual payroll summary subtracts estimated reserved payroll from the remaining annual allocation. This is currently frontend-persistent storage; a backend estimates endpoint would be needed for shared multi-user persistence.

10. Internal Revenue Workflow

Internal Revenue is a spreadsheet-like module for BS, Inter, registration, government dues, project, and other revenue heads.

  • Revenue period is stored by month, converted to a YYYY-MM period key.
  • Cells load from GET /api/v1/internal_revenue_cells?period=YYYY-MM.
  • Cells save through POST /api/v1/internal_revenue_cells/bulk_upsert.
  • Formula columns are not directly editable.
  • Formula logic calculates BS total, Inter total, Grand Total, Total Expense row, and Closing row on the frontend.
  • Edits are buffered in a pending-save map and flushed to backend; localStorage also stores rows for immediate browser persistence.
  • Export creates a printable/exportable report layout from selected sections.

11. Reports Module

Reports load summarized backend data from GET /api/v1/reports. The user can switch Weekly, Monthly, or Yearly period display using Ant Design segmented control and date picker.

Report Techniques Used

  • No external chart library is used.
  • Report chart bars are custom HTML/CSS progress bars.
  • The width of each chart bar is calculated as value / maxValue * 100.
  • Tables are Ant Design Table components.
  • CSV export is generated in the browser using Blob, URL.createObjectURL, and a temporary download link.
  • Report rows are normalized from backend series arrays using helper functions such as sumSeries and makeRows.
  • Status breakdowns use Ant Design Tag and Progress components.

13. Audit Logs

Audit Logs list system activity from GET /api/v1/audit_logs. The UI supports module, action, user, role, date-range, and text filters.

  • HOI/admin/superadmin can view all logs when backend allows.
  • Other permitted users see logs according to backend response.
  • Frontend formats raw actions into readable labels: create, update, delete, approve, reject, submit, verify, generate, login, logout, activation, password, and bulk_upsert.
  • Internal revenue spreadsheet changes are summarized by period, changed cell count, and preview values.

14. Notifications

Notifications load from GET /api/v1/notifications. Header unread count is loaded inside AppLayout when the user has view_notifications.

  • Single notification read state uses PATCH /api/v1/notifications/:id.
  • Mark all read uses PATCH /api/v1/notifications/mark_all_read.
  • Notifications show title, body, category, read/new tag, and optional link path.

15. Settings and Profile Workflow

Settings lets each user maintain profile details, avatar, and password.

  • Profile loads from GET /api/v1/profile.
  • Profile update uses PATCH /api/v1/profile.
  • Password change uses PATCH /api/v1/profile/password.
  • Avatar upload uses a hidden file input, object URL preview, react-easy-crop cropper, canvas crop utility, and Base64 image data sent to backend.

16. API Client and Data Handling

  • Default API base URL is http://localhost:3002.
  • It can be overridden with VITE_API_BASE_URL.
  • All API requests are JSON and include Content-Type: application/json.
  • Authenticated calls include Authorization: Bearer <token>.
  • Response parsing handles JSON and plain text.
  • HTML backend error pages are converted into a safer message: “Server error. Please try again.”
  • On 401, local auth state is removed and user is redirected to login.
  • There is an audit-writing helper in the API client, but shouldWriteAuditLog() currently returns false, so automatic client-side audit writing is disabled. Explicit logout audit call still exists.

18. Frontend Validation and UI Patterns

  • Ant Design Form rules enforce required fields, email format, and required selections.
  • Budget amount input sanitizes digits and decimals.
  • Budget duplicate checks prevent overlapping category budgets in the selected year range.
  • Modal discard confirmations protect unsaved user, budget, request, payroll, and staff edits.
  • Archived payroll years and previous-year budgets are locked from mutation.
  • File uploads are converted to data URLs for request attachments and user images.
  • Responsive design uses CSS flex, grid, media queries, Ant Design breakpoints, and horizontal table scroll.

20. Current Limitations / Notes

  • The complete authoritative role-permission matrix is controlled by the backend and is not fully visible in this frontend repository.
  • Payroll annual allocations, archived payroll years, saved payslips, and payroll estimates are currently stored in browser localStorage in the frontend. For multi-user production use, backend persistence endpoints should be added.
  • The newly imported payroll sheet data is based on the readable rows in the supplied image. Some blurred names may require manual correction in Staff Master.
  • Reports period controls currently change the displayed period label and export filename; the frontend calls a single reports endpoint without sending period filters.
  • Expense Management route currently points to a placeholder page.

21. High-Level Data Flow

  1. User authenticates and receives token.
  2. Protected route validates token and refreshes user permissions.
  3. AppLayout filters navigation using permissions.
  4. Module page loads data from its API wrapper.
  5. User performs an action through forms, tables, modals, drawers, or popovers.
  6. API wrapper sends JSON request to backend with bearer token.
  7. On success, page reloads affected data and shows success message.
  8. On failure, page shows backend or generic error message.
  9. Reports and dashboard transform loaded arrays into cards, tables, progress bars, and custom charts.

22. Future Enhancements

  • Add backend database tables and APIs for payroll estimates, annual payroll allocations, saved payslips, and archived payroll years so this data is shared across all users and devices.
  • Complete the Expense Management module and connect approved requests with actual expense entry and budget deduction.
  • Add full PDF export for reports, payroll estimates, internal revenue sheets, and approval summaries.
  • Add advanced charts using a charting library if future requirements need interactive graphs, drill-down analytics, or printable dashboards.
  • Add a backend-driven role-permission management screen so administrators can edit permissions without code changes.
  • Add Excel/CSV import for payroll staff and internal revenue data to reduce manual data entry.
  • Add stronger validation for CNIC, bank account/IBAN, payroll year ranges, increment dates, and duplicate staff records.
  • Add notification delivery through email or SMS for request approvals, payroll cycle approval, rejected requests, and password/security events.
  • Add backup/restore and audit export features for administrative record keeping.
  • Add multi-step approval configuration for departments if the college later needs more approval levels.

How to Show the Database to Examiner

There are three practical ways to demonstrate database data during viva:

  1. Through the application UI: Open modules such as User Management, Budget Management, Payroll Management, Internal Revenue, Reports, Audit Logs, and Notifications. This is the best user-facing demonstration because it proves the database is connected to the system workflow.
  2. Through API responses: Use browser developer tools or curl commands to show backend JSON responses. This proves the frontend is not static and is receiving database-backed data from REST APIs.
  3. Through database console/tool: Open the backend database using the relevant database client and run queries against the main tables.
